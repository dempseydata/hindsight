# CONTEXT.md — hindsight domain glossary

One local application over Claude Code data, two views in v1: **where** (where did my tokens go) and **what** (what did I actually do). The third framed view — **why** (why did my process change) — was dropped wholesale from v1 (ADR-0006); its silent-change backstop *capture* stays but renders nowhere. A different third view — **how** (how did I get here) — is decided for post-v1 (ADR-0010, ticket #54). Sole v1 user is the operator. Decision rationale lives in `docs/adr/`; this file owns the vocabulary. Terms below are the canonical names — don't drift to synonyms.

## Sources and ingest

- **Transcript** — a session's JSONL file under `~/.claude/projects`. The archive source: months of backfill, survives independently of extraction.
- **Subagent transcript** — a spawned subagent's own JSONL at `<project>/<session>/subagents/agent-<id>.jsonl` (issue #13, ADR-0019). Never "child transcript": the name matches the directory, the OTEL `query_source=subagent` attribute and the `SubagentStop` hook. Its `usage`, `tool_events` and `command_grains` rows are filed under the **parent session**, agent id on each row; it is never a `sessions` row. Recorded per parent in `subagent_transcripts` with its size, so growth is detected per transcript and rides the ordinary top-up path — which is also how sessions synced before ingestion gained theirs. A fresh one holds its parent live. Self-exclusion is inherited from the parent. **The audit is blind to subagents by design**: the extract, the what-pass and the re-audit threshold read the parent transcript alone, so a subagent appearing or growing never rewrites an entry.
- **Parent session** — the session a subagent transcript is filed under. A **session** means the operator's session *including everything it spawned*.
- **Agent id** — the subagent's `agentId`, kept on every substrate row it emitted (NULL on the parent's own rows) so a per-agent breakdown is a query, never a second session. Rendered as two numbers only — *N subagents* on the ledger row, the count and token share as a where-view tile — no per-agent rows.
- **OTEL telemetry** — the opt-in push feed (OTLP/HTTP JSON, `/v1/logs` + `/v1/metrics`). The enrichment source: edit decisions, api-error detail, MCP attribution. Push-based and unretried — lost if nothing is listening.
- **Ingest listener** — the single sanctioned background process (ADR-0001): receives OTEL, writes rows, does nothing else. Everything else is on-demand.
- **Coverage window** — the honesty rule for OTEL-fed metrics: state when continuous capture began; never present a gap as a zero.
- **Day bucket** — the calendar day a row is filed under: always the operator's **local** day, converted at read time from the UTC timestamp actually stored (ADR-0014, ticket #74). Timestamps are instants and stay as the CLI wrote them; a day is an answer to "what did I do yesterday", which is a local-clock question. The zone is `HINDSIGHT_TZ` (an IANA name) when set, else the host machine's (issue #1, ADR-0014 amended); an unknown name warns once and falls back to the host. `sessions.date` is the one *stored* bucket, re-derived from the transcript head on every analysis run so a zone change cannot leave it a day off its own usage bars; a vanished transcript keeps the date it has.
- **Analysis run** — the on-demand entrypoint: sync transcripts → extraction → backstop capture → sunk-cost scan → assemble. Batch on launch plus manual refresh; a *separate* control from the where-view's metrics refresh.
- **Live-session guard** — a transcript modified within the last 5 minutes is a live session: the analysis run leaves it pending rather than extracting mid-flight (ticket #29), and leaves its substrate alone rather than wiping rows the same run will then decline to refill (ticket #76). Once quiet, a session whose transcript grew since sync has its scanned substrate topped up whatever its status, and its cached extract and what-pass outputs invalidated when the audit is due a rewrite (ADR-0013).
- **Self-exclusion** — hindsight's own `claude -p` analysis sessions are excluded from ingestion and analysis by default (ADR-0003), detected by prompt signature.
- **Session status** — the lifecycle of a synced session: `pending → done | empty | lost`, with `partial` meaning *retryable, next run* (a failed or gated-out model call, an unreadable transcript). **Lost** (ticket #78, ADR-0015): the transcript is gone and no cached extract exists — nothing to read, so no retry can ever succeed; terminal and never selected by the run queue. Distinct from **empty** (readable, nothing in it) and **SKIP** (a verdict on content). A `lost` session keeps whatever substrate it had (unknown, never zero) and renders in the *what* ledger as its own dim one-liner, counted as *unrecoverable* rather than *awaiting analysis*. Decided at analysis time by an explicit existence test, never inferred from an extraction error, and drained from the backlog on first contact — no migration.
- **Greedy extract pass** — the step of the analysis run, ahead of the model loop, that either marks a quiet `pending`/`partial` session `lost` or caches its extract, with no model call. Once the extract is on disk, pruning the transcript loses nothing — this is what closes the retention race that created the backlog.
- **Limit exhaustion** — subscription usage limits hit mid-run. A designed pause, not a failure: sessions stay pending, the next run resumes (ADR-0003).

## Extraction (ADR-0002)

- **Extract** — the role-prefixed conversational text of one session (user + assistant text blocks only; tool results excluded), ~2% of transcript size.
- **Piece / piece index** — one numbered extract entry (`[17] USER: …`). Indices are session-global and continuous across parts.
- **Part** — one chunk of an extract under the 180K-char cap. Multi-part sessions are the rare overflow case.
- **What-pass** — the extraction call producing one audit entry per session. Strict four-section markdown; integrity checked by the weekly spot-check. Since `what-v3` (ADR-0016) the prompt brackets the extract — framed as data, output contract restated after it — and carries its own regression set (`eval/what_cases.json`, `eval/what_run.py`: 10 formerly-poisoned parts + 10 good, scored by `valid_entry`), run before any prompt or model-pin change. A gate rejection prints one `rejected <part>.md` line to stderr.
- **Merge call** — the extra what-pass call that folds multi-part entries into one, preserving the one-entry-per-session invariant.
- **Contract gate** — write-time validity check on every what/merge output (ticket #38): an entry opens `###` or is a SKIP verdict; anything else (refusal prose) is a failed call — uncached, retried next run, never stored as an audit row. The backfill import applies the same gate, downgrading a refusal-cached session to pending.
- **Model pin** — `claude-haiku-4-5-20251001`. Transport (`claude -p` vs API) is implementation detail.
- **Prompt version** — identifier carried on every audit row naming which prompt produced it; bumped by any prompt edit.

## Audit (ADR-0004)

- **Audit entry** — one per session, flat: title / **Did** / **Decided** / **Setup changes**. Stored in one cross-project audit table; per-project separation is a query, not a file layout.
- **Active day** — a local day on which a session has a usage row. The what-view ledger files a session under **each** of its active days in the window (issue #9), so the ledger and the chart agree on which days are empty; a session without usage is filed under its start day alone. The entry is the same one under every day — it summarises the whole session, not that day's work — so a day after the first carries a continuation note (*started 2026-09-04 · day 5*, calendar days), and the coverage counts count the session once. Undated sessions are always shown. Not a second audit row per continuation, rejected in ADR-0013.
- **Prefix semantics** — an audit entry covers the session as of its analysis run, and a resumed session keeps its original entry *until a quarter of the transcript is unseen by it* (`REAUDIT_SHARE`), at which point the entry is rewritten from the whole (ADR-0013, ticket #73). Applies to the audit alone: `usage`/`tool_events`/`command_grains` are mechanical facts and are always topped up on growth, whatever the status. Pre-done truncation is prevented by the live-session guard (ticket #29).
- **Audited size** — `sessions.audited_size`, the transcript size an audit entry covers; the watermark the re-audit threshold is measured against, so incremental resumes accumulate instead of resetting it. NULL means no evidence of what the entry saw (a backfill-imported session), which never re-audits on size grounds.
- **Stated-rationale convention** — a Decided line carries rationale only when stated in-session, as close paraphrase or quote; nothing invented when none was stated.
- **SKIP** — the what-pass verdict on a trivial session: row kept, no markdown.
- **ADR count** — distinct files under the project's `docs/adr/` created or modified during the session, derived mechanically from tool events. Semantics "ADRs touched"; never model-emitted.

## Silent-change backstop

- **Silent change** — a setup change with no conversation about it (auto-updates, machine-driven config edits). The model must never attribute these; the backstop owns them.
- **Snapshot** — analysis-time capture of the `~/.claude` text-config surface. First run is the **silent baseline**.
- **Blob** — content-addressed (sha256) stored config content. Diffs are computed at render time, not stored.
- **Change event** — one detected change, from one of three sources: project `.claude` git commits, snapshot diffs, structural `installed_plugins.json` diffs. Captured but rendered nowhere and linked to nothing in v1 (ADR-0006); every change event effectively reads "changed, no stated rationale".

## Where-view substrate

- **Sunk cost** — what a session pays at start before the first prompt: the CLAUDE.md chain (@-imports expanded), skill and command descriptions, MCP config. Itemised per project in `sunk_cost` (user-scope rows carry NULL project; plugins are the grouping level); plugin registry keyed by install path (the ccwhere double-count fix). MCP rows are config-JSON size, a proxy for the wire schemas servers actually serve; size/4 estimates throughout — the measured median carries authority.
- **Tool events** — JSONL-derived per-session tool_use/tool_result records, paired by tool-use id and filled during sync, one row per call (streamed duplicates deduped; a tool_use whose name holds command text is malformed and skipped); substrate for ADR counts and per-skill/MCP/CLI usage. Each row carries its consumer classification, a per-call error flag from the paired tool_result (NULL when unpaired — unknown, not ok), and the emitting message's API id — collectively the **grains** (ticket #42).
- **Consumer** — who a tool call is charged to in the where-view league: `skill` (the Skill tool's skill), `mcp` (server, with the tool split out), `cli` (program parsed from a Bash command and found outside OS-shipped paths, or no longer on PATH at scan time), `shell` (OS-shipped binaries and shell builtins — ubiquitous, unprunable), or `builtin` (the tool itself; also the fallback when a Bash command's program is unextractable). Machine-derived at scan time, never a curated list.
- **Session lens / message lens** — the league's two token attributions: session lens hands a consumer the whole usage of every session it appeared in; message lens joins tool events to `usage` by message id, charging only the API responses that actually invoked it. Agreement across lenses is the signal.
- **Usage** — JSONL-derived token counts by model, one row per API response (deduped across the records streaming one response), filled during sync. Tokens per session/day/project are plain SQL, regardless of OTEL coverage.
- **Self-instrumentation hook** — `build/hook.py`, registered per hook event in `~/.claude/settings.json` (the config snippet is in its docstring). POSTs one `hindsight.hook` event per firing to the ingest listener — at SessionStart carrying the session's folder identity (ADR-0018); fails silently within a bounded timeout when the listener is down. The hook panel's only data source — OTEL emits no hook telemetry.
- **`hindsight.hook` event** — the hook's row in `otel_events`, distinguishable from Claude-emitted events by name. Carries `hook.event` (which hook fired), `hook.duration_ms` (wall time of the script body only — the clock starts after spawn + interpreter startup and stops before the POST; it measures the instrument, not the session's cost), and `hook.cpu_ms` (process CPU including interpreter startup — the per-firing cost figure the hook panel charts; ADR-0005). A firing's true wall cost — spawn to exit, including timeout waits — is visible only to the spawning harness and is not captured.
- **Reliability panel** — the where-view panel over OTEL `api_error`, `api_retries_exhausted` and `mcp_server_connection` (issue #14): retries per model with the wall time lost to exhausted retries, and per-server MCP connection health (attempts, failures, the failure share, connect median). States retries and wall time, never spend — these events carry no token counts. Under the coverage-window rule: a window before capture reads as a stated gap. Each row's evidence is its session ids; self-excluded sessions are out, a session sync never saw counts with its project unknown (never dropped), and `disconnected` is a clean close, not an attempt.
- **Substrate scan** — the one full transcript parse that fills tool events, usage and command grains, over the parent transcript and its subagent transcripts in one pass (ADR-0019). Unknown record types are counted-and-skipped, never fatal; a session whose transcript vanished before scanning reads unknown (NULL), not zero.

## Schema-drift guard (issue #15, ADR-0020)

- **Field contract** — the list of every transcript key the substrate scan, the extract and the head scan depend on being present, as (scope, key): `FIELD_CONTRACT` at the top of `build/substrate.py`, enumerated from the three readers. A key added to a reader is added here; the guard walks this list, so the two cannot drift apart. Keys read but not expected present (`isMeta`, `is_error`, a file tool's `file_path`) are deliberately outside it.
- **Field histogram** — the guard's evidence: per record **version** (never per run or per session — one transcript can hold records from two CLIs), per record type, the record count and the presence count of every key one level deep — top-level, `message`, `message.usage`, the content block types and each block type's keys. Counted by the substrate scan as it goes, stored per session in `field_histogram` (so every rescan wipe keeps it exact and a schema-bump rescan never double-counts), summed per version when compared. Accumulates across runs.
- **Breakage** — a run-level, dated observation that the transcript shape moved under the parser: the run completed, the numbers since may be thin, here is why and since when. Written when the newest version with enough records differs from the nearest earlier one: a contract key **thinned** (present in >90% before, <50% after — tier *problem*), a top-level key **added** (absent before, >50% after — tier *informational*, the rows cannot be wrong), or this run's **skipped share spiked** past 3× the recent median (*problem*; the one per-run condition — a parse failure is a run-time event). Never halts ingest. Never a session status: `sessions` rows stay untouched, the row carries the date range. Surfaced as a banner on all three views for every tier and as a macOS notification for the thin-rows tiers only — a notification always means a decision is needed. Cleared by the operator alone.
- **Acknowledge** — `analyze.py acknowledge-breakage <id>`: closes one breakage row, and its new version is the comparison baseline from then. A judgement about the alert and nothing else — never a rescan. A parser fix ships as a code change plus a schema-version bump, which rescans through the existing mechanism: two operator actions, each with one meaning.
- **Version line** — the installed CLI's `claude --version`, printed once per run to the log. A record, never a trigger: the guard fires on the shape, not on the version string.

## Project identity (ADR-0018)

- **Project** — a workspace folder *as a thing*, identified by its folder identity, never by its name. A project's name is an attribute that can change; its history — sessions, trail, narrative — stays with the folder through any rename. A fork, clone or copy is a different folder and so a different project: history is never carried from an old folder onto a new one. Every project-scoped table keys on the project's **current name**; there is exactly one name per project in the database at any time.
- **Workspace folder** — a directory under the workspace root (one repo per folder). The transcript directory name Claude Code derives from its path is a *name-time* fact: the same encoded name can serve different folders at different times (name reuse), so it is the fallback attribution, not the identity.
- **Folder identity** — the folder's inode, as the filesystem reports it. Stable across a rename on the same volume; new for a copy, a cross-volume move, a clone or a fresh folder — which is exactly the boundary the project term wants. Recorded per session by the self-instrumentation hook at SessionStart, and per name by the analysis run's presence observation.
- **Attribution source** — how a session came to be assigned to its project, one of three: *hook* (the session's folder identity was stamped live at SessionStart — exact), *operator* (stamped after the fact by the attribute command — the escape hatch for sessions predating the hook and for moves the filesystem cannot show), or *name* (no identity recorded: the session keeps the name it was synced under, and is hidden or shown by that name alone — the coverage-window rule applied to identity). Never inferred from a presence flip or a name resemblance.
- **Rename** — the same folder identity observed under a new name. Observed, never declared in the workspace: the analysis run re-keys the project's rows to the current name (canonicalisation at analysis time) and the how-view keeps every *former name* — for matching write paths under the old root, and for the "formerly …" line in its header. A rename is not a deletion and re-keying is not history being re-shaped: the rows always belonged to that folder.
- **Name reuse** — a name released by a rename and taken by a different folder, so one transcript directory holds sessions of two projects. Resolved by folder identity alone: a session with a hook or operator stamp goes to its folder whatever the directory is called; a name-only session in a reused name is a known ceiling, stated, not guessed at.
- **Former name** — a name a project carried before its current one, kept from presence history. Read by the how-view; rendered nowhere else — chips and ledger show current names only.

## The evolving collection (ticket #51)

- **Hidden project** — a project whose folder was absent, under any name it has carried, when the last analysis run looked (a renamed folder is present under its new name — ADR-0018). Exactly two states, present or hidden — no third "retired" state and no curated list: the operator's own deletion or archival of the folder is the marker, and the analysis run merely observes it. Observation is analysis-time, never render-time: the server renders the stored observation, so a deletion takes effect at the next analysis run, and a recreated folder likewise returns at the next run. Hiding is navigation-only and means exactly one thing: no chip. Ledger rows, chart segments, league entries and totals are untouched — a hidden project's data behaves like a chipless tail project's (present, counted, no one-click filter), and history is never re-shaped by later deletions. A reveal control restores hidden projects' chips. A dash-encoded name counts as present if *any* decoding of its dashes resolves to an existing directory (subdirectory sessions of live projects must never false-hide). Distinct from transcript pruning, where absence means *unknown*, not deleted.

## The how-view (ticket #54, ADR-0010)

- **How-view** — the post-v1 third view: the process actually followed in a project, told per project (the folder, through its renames — ADR-0018) as a status narrative over a ledger of phase runs, answering "how did I get here". Not the dropped why-view resurrected: no rationale attribution, no verdicts.
- **Process trail** — the how-view's raw material: command grains, skill invocations and file writes under the project root — the current one or any former name's (ADR-0018) — (one step per file per session — the first touch) for one project, assembled mechanically in date order (`build/how.py`). Audit titles supply the human-readable sentences of the runs; the only model prose is the status narrative (ADR-0012).
- **Command grain** — a user-typed slash-command invocation, parsed verbatim from a transcript's user messages (a user message *starting* with a `<command-…>` marker — the starts-with rule excludes quoted markers inside pasted extracts). The deliberate-process signal: a typed command injects its skill without a Skill tool call, so it is invisible to tool events and is captured by the substrate scan into its own `command_grains` table (ticket #61) — live now, ahead of the how-view that reads it.
- **Process declaration** — the machine-readable frontmatter of a project's `.claude/my-process.md` (the only location read): an ordered list of the project's own stages, each mapping to stage markers. Authored per project with its route already resolved — branching (e.g. the two design routes) lives in prose, never in the schema. The prose below the frontmatter remains the authority on meaning. Schema — a strict hand-parsed YAML subset, whole-segment name matching, loud invalidity — is ADR-0011. Project-level and optional: absence is a designed state — the project simply has no how-view.
- **Declaration states** — the three parse outcomes (ADR-0011): *absent* (no file or no fence — the project is not shown in the how-view at all; ticket #64 amendment to ADR-0010), *invalid* (fence fails the strict subset — raw trail plus a visible one-liner naming reason and line; a fence written wrong is never indistinguishable from one never written), *valid* (the stage-anchored view). Invalidity is total — no partial salvage — and includes duplicate markers across stages: bucketing ambiguity is rejected at parse time, resolved at authoring.
- **Stage marker** — an observable (command, skill invocation, phase-folder write) declared in the process declaration as evidence of a stage. Command and skill markers form one name pool matched against both capture paths; path markers bucket by longest matching prefix (ADR-0011 amendments). The how-view's anchor vocabulary: trail events are bucketed by stage through these markers, making back-and-forth between stages visible.
- **Phase run** — the how-view's unit of display (ticket #64): a band of consecutive trail events sharing one stage, at least three long (shorter runs fold into the run before them), rendered newest first with its date range and the audit titles of its sessions. A session straddling runs is titled only in the run holding most of its events. Back-and-forth between stages is visible as the alternation of runs. Off-script events band the same way under the one label `off-script` (issue #17): an **off-script run** is a run whose stage is that label — never a declared stage, never in the stated-process panel, rendered in the off hue.
- **Run ledger** — the ordered list of a project's phase runs with stage, date range and audit titles: the mechanical spine of the how-view and the sole input to the status narrative.
- **Status narrative** — the one model-written artefact in the how-view (ADR-0012): a bounded fact list per project synthesised from the run ledger, in three fixed groups — Built, Reversed, Now — each line dated and traceable to ledger entries. Load-bearing model output, so it carries a frozen eval set and threshold (`eval/`), is stored and gated like an audit, and degrades to the mechanical status when absent. Stored one row per project in `status_narrative` (`build/analyze.py` `refresh_narratives`, ticket #68): written after the session loop only when the ledger's content hash, prompt version or model changed; write-time gated by the eval's ground-truth-free floors (`eval/score.py` `contract`); a stored row whose `ledger_hash` no longer matches the live ledger is stale — a gated-out regeneration keeps the last good one.
- **Off-script activity** — trail events matching no declared stage. Informative, never a verdict — and the declaration's rot detector: a renamed skill surfaces here instead of silently vanishing from its stage. One lane, one term: it carries no judgement about whether the work was upkeep of the project's skills or a step the declaration has not caught up with — that reading stays with the operator. Off-script events form phase runs (issue #17) and so reach the run ledger and the status narrative, not only the aside's list.
- **Session boundary** — a command that opens a session rather than marks a process step: `/clear`, `/model`, `/compact`, `wayfinder`. A fixed set in the view, not a declaration key; an unclaimed boundary is set aside from off-script and stated in its total, never silently dropped (ADR-0011, #70) — and never a run event, since a compaction inside an off-script run would otherwise read as a step of it (#17). A declaration that claims one under a stage wins.
- **Juxtaposition rule** — the comparison posture: the view surfaces presence, first/last-seen per stage and the off-script list, and renders the stated process beside the trail. No order rules, no conformance verdicts, no model comparison; deviation is informative, and every judgement stays with the operator. A project without a declaration has no how-view; an invalid declaration still renders the trail with its error — a fence written wrong never hides.

## The so-what view (map #18, ADR-0021)

- **So-what view** — the charted fourth view: what only shows across N sessions of one project, stated against the project's own baseline. Two stages: **Stage A** is mechanical and reads stored tables only; **Stage B** is a model synthesis over compact digests, conditional on a design-time eval proving it adds anything over Stage A, and evaluated in full if built. Compares a project with itself, never with another project. Not the dropped why-view: no rationale attribution.
- **Pattern** — Stage A's unit: one cross-session fact with its numbers, window and baseline, and evidence pointers (session ids, tool-use ids, message ids). Carries no verdict — the juxtaposition rule (how-view) extended across sessions; judgement stays with the operator. The brief's "candidate" is a pattern, one term. A window that clears the sparsity floor with nothing above a magnitude floor reads *nothing to report*, never an empty list presented as a result.
- **Window** — the span a pattern is computed over: the shared header window exactly as the what and where views read it (filter state: presets 7/14/28/90/all, default 14, bar-click ranges), no chrome of the view's own (ADR-0022). Three states: **too thin** (below the sparsity floor, empty included — a coverage statement under the coverage-window rule, never a zero presented as a finding), **nothing to report** (clears the floor, no row clears its magnitude floor — a result), and patterns.
- **Baseline** — what a pattern's numbers are stated against, two kinds side by side: **preceding** (the window of equal length ending where this one starts) and **history** (everything before the window). Each is present only when it clears the sparsity floor, else *no baseline*; the two may disagree and both are shown (the juxtaposition rule across time). One definition for every signal — the baseline belongs to the pattern, not the signal.
- **Sparsity floor** — at least 3 sessions with usage and at least 3 active days, applied identically to the window and to each baseline. Sessions because the unit is cross-session; days because the cost trend is a per-day statistic. Values are greybox-calibrated knobs.
- **Magnitude floor** — per signal, gating the *row*: a pattern exists only when one of its rows clears its floor, and rows below it are dropped, never listed. Consumer: calls ≥ 10 and either error share ≥ 0.10 or token share ≥ 0.25, reason carried. Cost trend: |median work-per-day lift| ≥ 0.30, mean stated beside and never gating. Drift: a newly off-script name or top-level write path at ≥ 3, off-script share always stated. Knobs, calibrated at the greybox.
- **Absent** — a signal whose input does not exist for the project (drift with no valid declaration): stated as absent, a fact about the project rather than the window — never zero, never nothing to report.
- **Finding** — Stage B's unit, if Stage B is built: a model-written "so what" tracing to at least one pattern. The only place a verdict lives. Load-bearing model output: frozen eval set, threshold before the prompt, stored and gated like the status narrative.

## Served UI (ticket #83)

- **Theme** — the served UI's palette state: **dark** (the incumbent — the shipped V3 Indigo deck, ADR-0007) or **light** (a constrained derivation of the same direction, ADR-0017). Canonical term — never "mode" or "scheme". One direction, two themes: a theme changes token values, never layout, components or hues' roles.
- **Filter state** — the header's active chips, day window, preset, hide-cache-reads and reveal state, shared by the what and where views. Lives in the browser per tab (`sessionStorage`, issue #10) and is restored before the first render, so a view switch or reload keeps it; on restore a hidden project's chip is active only alongside the reveal state that showed it (ADR-0009). Gone when the tab closes; never on the server. The how-view has no filter chrome and reads none of it, but the two selections are one: the what/where how-link carries the active chip as `?p=`, and a how-view opened with `?p=` writes that project back as the active chip.
- **Theme pin** — the viewer's explicit theme choice, overriding the OS signal. The toggle has three states: *system* (follow the OS preference), *pinned light*, *pinned dark*. The pin lives in the browser, never on the server — the server renders identically for everyone.
