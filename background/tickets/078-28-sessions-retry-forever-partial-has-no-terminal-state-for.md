# #78 28 sessions retry forever: 'partial' has no terminal state for a pruned transcript

state: closed · labels: bug, ready-for-agent · opened: 2026-08-29 · closed: 2026-08-30

## Symptom

28 sessions have sat at `status='partial'` since July. Every analysis run selects them, every run fails them, and nothing changes. Confirmed against the live DB after the run of 2026-08-29: `{'done': 256, 'partial': 28, 'pending': 1}` — the partial count and its date span are identical before and after.

## Root cause

**All 28 transcripts are gone.** Their span is 2026-06-26 to 2026-07-23, past Claude Code's transcript retention.

```
partial: 28, transcript MISSING: 28, present: 0
```

`run_analysis` selects `WHERE status IN ('pending', 'partial')`. `process_session` calls `extract_session`, which raises `ExtractionFailed` on a file that no longer exists, marks the session `partial` and returns (`build/analyze.py:844`). Next run, same selection, same failure.

`partial` encodes "retryable, next run". For a pruned transcript the retry is *structurally* incapable of succeeding — there is no state meaning "unknowable", only "not done yet". The queue has no exit.

## What it costs

- **Cheap per run.** Extraction dies before any `claude -p` call, so this burns no tokens and barely any wall-clock. It is a correctness and honesty problem, not a cost one.
- **A month of history that can never be audited.** None of the 28 has an audit row, so none will ever produce a ledger entry in the *what* view — absent silently, not marked as a gap.
- **A permanently wrong queue.** "28 outstanding" is reported forever and can never be worked off.

| `-Applications-Open-Design…-prebundled` | 10 | 07-03..07-04 | 0 | 0 |

Only 6 of 28 were ever substrate-scanned (`skipped_records IS NOT NULL`); 266,377 tokens are counted from the 6 that have usage rows. The other 22 read *unknown, never zero* — which is the correct existing behaviour, and worth preserving in whatever fix lands.

## The decision this needs

This is not a one-line fix, because it touches the coverage-honesty rule the product already legislates elsewhere ("a vanished transcript keeps its old rows"; "pruned transcripts read unknown, never zero"; ADR-0009's insistence that history is never re-shaped by later deletions).

Open questions, deliberately unanswered:

- **A terminal status** (`lost`?) excluded from `todo` — or a retry-count / age bound on `partial`?
- **Silence or gap?** Should the *what* view show these as an explicit coverage gap rather than omitting them? The chart already renders missing days as gaps rather than zeros; the ledger has no equivalent gesture.
- **Does "unknowable" differ from "trivial"?** `empty` and SKIP rows already render as dim one-liners. This is a third thing: not skipped, not audited, unrecoverable.
- **Retention race.** Anything sitting in `pending`/`partial` long enough will hit this. Is the real defect that sessions are allowed to age past retention un-extracted at all — i.e. should a first-pass extraction be greedier?

Front door is `/grill-me`: pick the shape before building it.

## Agent Brief

**Category:** bug
**Summary:** Give the what-pass queue a terminal `lost` status for sessions whose transcript is gone and unextracted, surface them honestly in the ledger, and extract greedily so the race that created them cannot recur.

**Corrections to the report above, established during triage (2026-08-29):**
- 27 of the 28 are structurally unrecoverable. The 28th (`296cf33f`, career-ops, 2026-06-26) has a good cached extract and a poisoned cached what-output that fails the contract gate, so it fires a real model call every run — a different defect, split out to its own issue. "Burns no tokens" is therefore false for that one.
- The 27 are **not silent**. The ledger's LEFT JOIN renders them today as *"synced, not yet analyzed — run an analysis"* and counts them under *awaiting analysis* — a false instruction, since the server has no way to tell *not yet* from *never*.
- Origin: 22 entered via the backfill import (2026-08-17) with no cached extract — transcripts already pruned, dead on arrival. 6 (the five `ccwhy` scratchpad sessions of 07-23 and one `hindsight` session) have `usage` rows, so they were on disk at substrate-scan time and were lost because the model loop never reached them before retention — extraction lives inside the per-session pass, behind the limit-exhaustion pause.

**Current behavior:**
`run_analysis` selects `status IN ('pending','partial')`. `process_session` extracts on demand; a missing transcript raises `ExtractionFailed`, the session is re-marked `partial`, and the next run repeats it. Nothing can ever leave the queue. The ledger renders any session without an audit row as pending.

**Desired behavior:**
1. **Terminal `lost` status.** A session is `lost` when its transcript no longer exists **and** no cached extract (`<sid>.map.json` in the extracts dir) is available. The check must be an explicit existence test, not inferred from `ExtractionFailed` — that exception also covers unreadable/malformed files, which remain retryable. `lost` is never selected by the run queue. It is decided at analysis time (ADR-0009: observe at analysis, render stored state), and by **natural drain** — no `user_version` migration; the run loop classifies the backlog on first contact.
2. **Greedy extract pass.** Before the model loop, extract every `pending`/`partial` session whose transcript exists and is not live (the live-session guard applies). No model calls. Once an extract is cached, pruning the transcript loses nothing. `ExtractionFailed` here is swallowed — the session stays retryable.
3. **Ledger gesture.** A `lost` session renders as a dim one-liner, sibling of *trivial session — skipped* and *synced, not yet analyzed*: wording along the lines of *transcript pruned before analysis — unrecoverable*. The LEFT JOIN rule (the ledger never omits a session the coverage line counts) is preserved. The what-view summary line gains its own term (`· N unrecoverable`); *awaiting analysis* counts only genuinely pending sessions. This makes `sessions.status` a view input for the first time — deliberate.
4. **Substrate untouched.** `usage`/`tool_events`/`command_grains` rows of a `lost` session are kept; sessions never scanned keep NULL — unknown, never zero. Nothing about `lost` re-shapes history.
5. **Domain docs.** `CONTEXT.md` gains a session-status lifecycle entry (`pending → done | empty | lost`, `partial` = retryable), contrasting `lost` (nothing to read) with `empty` (readable, nothing in it) and `SKIP` (a verdict on content). One ADR records condition-over-budget (rejected: retry count / age bound — a policy dressed as a fact) and the naming (`pruned` rejected because done-and-pruned sessions exist; `unknowable` kept for prose).

**Key interfaces:**
- `sessions.status` — new value `'lost'`; `_mark` unchanged.
- `run_analysis` — greedy extract loop ahead of the `todo` walk; `todo` selection excludes `lost`.
- `process_session` / `extract_session` — the existence check that decides `lost` vs retryable.
- The ledger query and `rowHtml`/summary in the what-view — status joined in, third dim row, new summary term.
- `import_backfill.classify` — unchanged; imported no-extract sessions still enter `pending` and drain to `lost` at the first run.

**Acceptance criteria:**
- [ ] A session with no transcript and no cached extract is marked `lost` by the run and never selected again; one with no transcript but a cached extract proceeds to the model pass.
- [ ] A session whose transcript exists but fails extraction stays `partial` (retryable).
- [ ] Before any model call, every selectable non-live session with a transcript on disk has a cached extract.
- [ ] After one run against the live DB: `partial` = 1 (`296cf33f`), `lost` = 27, `done`/`empty` counts unchanged, no `usage` row deleted.
- [ ] The what-view renders each lost session as the new one-liner; the summary reads `… · 27 unrecoverable`, and *awaiting analysis* excludes them.
- [ ] Tests cover the three status outcomes, the greedy pass, and the ledger rendering; existing tests pass.
- [ ] `CONTEXT.md` lifecycle entry and the ADR are written.

**Out of scope:**
- `296cf33f` and any retry bound / attempt counter on model-call failures (own issue).
- Recovering lost sessions from any other source.
- Changing substrate NULL semantics or the coverage-window rule.
- A `user_version` migration for the backlog.
