# #79 296cf33f retries a real model call nightly: poisoned what-pass cache, no audit row, no bound

state: closed · labels: bug, ready-for-agent · opened: 2026-08-30 · closed: 2026-08-30

> *This was generated by AI during triage.*

## Symptom

Session `296cf33f-45e4-413f-8344-f91ad2a785a0` (career-ops, 2026-06-26) has sat at `status='partial'` since the backfill import and fires a real `claude -p` call on **every** nightly run. Found while triaging #78, which it does not belong to: unlike the other 27 partials it is fully recoverable.

## What is on disk

- Transcript: pruned.
- `local-data/analysis/extracts/296cf33f….map.json` + `part1.txt` (162 KB): present, good content.
- `local-data/analysis/<PROMPT_VERSION>/296cf33f….part1.md`: present, **poisoned** — plain assistant prose ("All passing tests mean the system is good to go…"), not an entry, so it fails `valid_entry`.

## Mechanism

`extract_session` short-circuits on the cached map, so no `ExtractionFailed`. `call_cached` rejects the poisoned file, calls the model with the full 162 KB prompt, and — for reasons not yet established — gets nothing that passes the gate, returns `None`, and the session re-marks `partial`. The #38 migration could not sweep this: it reset sessions with bad *audit rows*; this one never got an audit row, only a bad cache file.

Unknown, and the point of this ticket: is the model refusing repeatedly, is the run pausing on `LimitExhausted` before it is reached, or something else? No run history exists in the DB, so it cannot be answered from stored state.

## Open questions

- Root cause of the repeated failure (diagnose before touching anything — deleting the cache file is a one-line experiment that also destroys the evidence).
- Whether unbounded retry of a failing model call needs a bound at all, or whether the fix is sweeping poisoned cache files. #78 deliberately rejected a retry budget for the status model; if a bound is needed here it should be argued on its own.

Front door: `diagnosing-bugs`.

The #38 migration reset only sessions with bad *audit rows*; this one had none, so the file survived. The gated `call_cached` now rejects it every night, re-calls the model, gets prose, returns `None`, re-marks `partial`. Cost ≈ 40k haiku tokens/night, no log line, no bound.

**Current behavior:**
`WHAT_PROMPT + "\n" + extract` — the instructions are the oldest tokens, the transcript's last turn the newest; the model answers that turn. `valid_entry` accepts only `###`/`SKIP` at the start. A gate rejection is silent: nothing is logged and the session retries indefinitely with no attempt record.

**Desired behavior:**
1. The what-prompt frames the extract as data, not a live conversation (delimited block; instructions repeated *after* it, or placed after it) — a new prompt version, regression-gated against `eval/` per the Evaluation rule before it replaces `what-v2`.

3. Poisoned cache parts under `done` sessions are dealt with explicitly — either re-analysed (delete the poisoned parts and merged output, reset to `pending`) or knowingly left, recorded either way.

**Why human, not agent:** three decisions —
- the eval threshold for the new prompt version (a prompt has no compiler; someone sets the bar before the run);
- whether re-analysing the nine `done` sessions is acceptable history re-shaping (ADR-0009) and worth ~15 multi-part calls;
- whether to loosen the gate to accept a `SKIP` on its own line anywhere (would have passed repro 1) — a change to the gate's contract, not a fix.
